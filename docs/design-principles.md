# OneSite 代码生成设计理念

## 目标

OneSite 的模型定义是唯一的业务事实来源。`site sync` 的职责不是维护另一套业务代码，而是把这个事实来源确定性地投影为后端 API、前端界面和运行时配置。生成器应当做到：相同输入得到相同输出；错误输入不改变已有输出；每个阶段只负责一种明确的转换。

## 分层与边界

生成过程按配置、模型准备、模型同步、内省、关系解析、资源同步、按模型生成和聚合生成划分。前一阶段只输出后一阶段所需的结构化数据或文件，模板只负责呈现，业务规则保留在 Python 阶段代码中。`ModelDefinition`、`FieldDefinition` 和 `ForeignKeyInfo` 是这些阶段之间的稳定数据契约；它们保留字典兼容性，以免模板层承担迁移成本。

`app/models/` 是用户可编辑的唯一模型源。`generated/backend/app/models/` 是完全生成的镜像目录：同步时复制当前源模型和所需内置模型，同时移除已经不在源中的旧副本。启用的插件会在镜像清理之后、模型内省之前向生成目录补充默认模型，但不会向用户的 `app/models/` 写入实现细节；同名的用户模型始终优先。这样删除模型会真实生效，也不会在后续内省中被“幽灵模型”重新发现。

## 安全性优先

配置读取是生成的事务边界。若存在 `site_config.py` 但无法执行、未导出 `SiteConfig`，或其值未通过校验，生成会立即失败；旧项目的 `site_config.json` 若 JSON 无效或顶层不是对象，也同样失败。绝不能把它们当作空配置并把默认值写回 `.env`。同样，任一模型模块无法导入时，生成整体停止，而不是跳过该模型并留下不完整的路由、外键或前端代码。

文件写入采用内容比较：未变化时不改时间戳，变化时明确报告更新。这个策略使 `site sync` 可以安全地重复执行，也让代码评审聚焦真实变化。

## 保留与删除的原则

只删除可以证明是生成输出的内容：目前是 `generated/backend/app/models/` 中不再属于当前源模型或内置模型的 Python 文件。用户在项目其他位置编写的代码不由同步过程清理。对于命令行和配置格式，除非有明确的迁移方案，不轻易删除外部可见的兼容入口。

本轮清理移除了未被调用的 CLI Jinja 渲染函数、相关未使用导入，以及未使用的 `cookiecutter` 运行时依赖。渲染现在统一通过 `codegen.render.generate_file` 进入带内容比较的写入路径，减少重复实现和依赖面。

## 测试策略

仓库级测试只收集 `tests/`，示例项目的测试仍作为各自生成项目的验证资产，不再被根目录测试误收集。回归测试覆盖配置失败不降级、模型删除同步和主要模板渲染场景。新增功能应优先测试生成后的文本或结构，而不是只测试内部辅助函数。
